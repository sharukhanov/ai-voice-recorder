# Исследование диктофона AIREC

## Устройство
- AliExpress: ALiandream «Цифровой диктофон», вариант «NEW AI VOICE RECORDER», 16 ГБ
  https://aliexpress.ru/item/1005009304093292.html
- Форм-фактор «карточка» 86×55×3.5 мм, OEM-устройство (вероятно, продаётся под разными брендами)
- Родное приложение: **AIREC** (AIREC LLC)
  - Android: `com.record.airec.google`
  - iOS: есть в App Store
- Передача записей на телефон — по Bluetooth (скорее всего BLE). Транскрипция/саммари — вероятно, в облаке производителя.

## Окружение пользователя
- Телефон: iPhone
- Компьютер: MacBook Air (Apple Silicon)

## Цель
Своё приложение, которое забирает записи с диктофона и делает нормальную
транскрипцию/саммари (облачный «ИИ» производителя заменяем своим).

## План разбора протокола
1. [ ] Проверить USB: виден ли диктофон как флешка (USB Mass Storage) и в каком формате файлы.
2. [x] BLE-скан с Mac (`bleak`): имя устройства, сервисы, характеристики, их свойства. См. «Результаты BLE-разведки».
3. [ ] Декомпиляция APK (`jadx`): UUID, команды, формат пакетов, кодек аудио, API-серверы.
   - Скачать APK из облачного контейнера не удалось (APKPure → 403), нужно скачать вручную в браузере.
4. [ ] Снять трафик родного приложения iPhone ↔ диктофон через PacketLogger
   (Xcode Additional Tools + профиль Bluetooth logging от Apple на iPhone).
5. [ ] Написать PoC на Python: подключиться, получить список файлов, скачать запись, декодировать аудио.
6. [ ] Решить стек приложения (iOS: Swift/CoreBluetooth или Flutter) и пайплайн ИИ (Whisper/LLM).

### Реклама
- Имя: `AIREC(BLE)`; на этом Mac UUID `127825C6-D4DC-DE94-6F2F-99E653A6A6F8` (CoreBluetooth-UUID, на другом компьютере будет другим).
- Объявляемые service UUID: `0000af47-…`, `0137735a-…`, `00897178-…` (база `-0000-1000-8000-00805f9b34fb`).
  В GATT-таблице их нет — вероятно, в них закодированы данные (ID/MAC/статус), а не реальные сервисы. Проверить по APK.
- Manufacturer data нет.

### GATT
Один кастомный сервис `0011200a-2233-4455-6677-8899dfdedddc`
(стандартные Generic Access / Device Information macOS не показывает):

| Характеристика | handle | Свойства | Гипотеза |
|---|---|---|---|
| `0011201a-2233-4455-6677-8899dfdedddc` | 9  | notify | ответы / события |
| `0011202a-2233-4455-6677-8899dfdedddc` | 12 | write-without-response | команды |
| `0011203a-2233-4455-6677-8899dfdedddc` | 14 | notify | поток данных (аудио/файлы?) |
| `0011204a-2233-4455-6677-8899dfdedddc` | 17 | notify, write-without-response | двунаправленный канал (управление передачей?) |
| `0011206a-2233-4455-6677-8899dfdedddc` | 20 | write-without-response | ещё один канал записи |

- Читаемых характеристик нет; за 10 с подписки на все notify устройство ничего не прислало →
  протокол «команда → ответ», нужны байт-коды команд (шаги 3–4). Наугад в write-характеристики не писать
  (риск стереть записи / сбросить устройство).

### Заметки по запуску на macOS
- Из процесса без Bluetooth-разрешения (например, из Claude Code) Python падает с SIGABRT (TCC:
  нет `NSBluetoothAlwaysUsageDescription`). Запускать из Terminal.app, разрешив ему Bluetooth.
- Первый запуск сразу после запроса разрешения может дать `BleakError: Bluetooth device is turned off` — просто повторить.
- Системный Python 3.9 + pip 21 не ставит `pyobjc-core`; помогает `pip install --upgrade pip` внутри venv.
